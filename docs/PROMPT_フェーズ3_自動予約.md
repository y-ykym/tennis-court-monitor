このリポジトリ(y-ykym/tennis-court-monitor)に、監視中の空き枠を自動で予約する「フェーズ3」を実装してください。
要件は本人と 2026-09-14 に詰め終わっています(§2)。設計の自由度は §4 に書いた範囲で残してあります。

## 1. 現状(変更してはいけない前提)

- フェーズ1: GitHub Actions(`check.js`、cron-job.org から 3 分おき、1 回の実行は約 90 秒)が空きを取得 → `lib/filter.js` で監視条件に絞る → `state.json` との差分で「新しく出た空き」だけ LINE にカード通知。カードの各枠に「<呼び名>で予約」ボタン(A/B、postback `book|<署名付きトークン>`)
- フェーズ1.5/1.6: LINE で「よやく」→ Worker が A・B の予約一覧カードを返す。各行の「キャンセル」→ 確認 →「はい」で Worker が取消 POST(`worker/src/index.js`, `site.js`, `cancel-token.js`)
- フェーズ2: 予約ボタン → Worker(`startBooking`)→ Cloudflare Tunnel → 自宅 Raspberry Pi 5 の `/book` → Playwright で予約(40〜90 秒)→ 結果カードを Pi が LINE に push。Pi は **同時に 1 件だけ**処理(409 busy)。reCAPTCHA v2 が出た回だけ「🔐 確認が必要です」カードで人に渡す。Pi の Docker イメージには `booking/` しか入っていない
- 監視条件(`lib/config.js`): 平日=猿江恩賜公園 19 時のみ、土日祝=猿江・亀戸中央・大島小松川の全時間帯(9/11/13/15/17/19 時開始の 2 時間枠)
- 予約者: `SITE_USER_A`(呼び名 `LABEL_A`)と `SITE_USER_B`(`LABEL_B`)。値は GitHub Secrets / Worker Secrets / Pi の `.env`
- ペナルティ: 利用日 ≤ 今日(JST)+3 日 の予約は取り消すとペナルティ(`worker/src/cancel-token.js` の `penaltyApplies`)。**利用日が今日から 4 日以上先なら、その日の 23:59 まで無料で取り消せる**
- 署名鍵 `BOOKING_SIGNING_SECRET` は 3 か所(Actions / Worker / Pi)で同じ値。新しい通信経路の認証はこれを流用する
- 自宅回線(SoftBank Air)は夜に不安定。2026-09-26 に安定する予定。Pi の生存監視(毎時、LINE に ⚠️/✅)は Worker Cron で稼働中

## 2. 要件(本人と確定済み)

| # | 要件 | 確定した解釈 |
|---|---|---|
| 1 | 監視中の枠に空きが出たら自動で予約する | 対象は `lib/filter.js` の監視条件を通った「新しく出た空き」。**空きのチェックは Pi 側で 1 分おきに行う**(理由と構成は §3)。Actions の 3 分おきは通知用にそのまま残す |
| 2 | ペナルティが発生する期間は自動予約しない | **利用日 ≤ 今日(JST)+3 日 の枠は対象外**(既存 `penaltyApplies` と同じ境界。`penaltyday` は 3 で固定してよいが定数として 1 か所に)。対象外の枠は従来通り通知(予約ボタン付き)。**利用日 = 今日+4 日 は対象に含める**(空きの 45% がここに出る。無料取消は当日 23:59 までなので #6 の警告を付ける) |
| 3 | 1 日につき最大 2 枠 | **利用日ごと**。**手動で取った予約も数える**。その利用日に予約者(平日=B/休日=A)の予約が 2 件あれば見送る。判定は予約実行時に**サイトの予約一覧(prwha1000)を実際に見て**行う(推測で数えない)。同じ実行で複数候補があるときは、成立した分も数に入れる |
| 4 | 場所の優先順位 | 平日: 猿江恩賜公園のみ。休日: **大島小松川 > 猿江恩賜 > 亀戸中央**。同じ利用日に候補が複数あるときの並び順は **公園の優先順 → 時間帯の優先順**。時間帯の優先順は **17 > 19 > 9 > 11 > 13 > 15**(開始時刻)。この順に上から試し、その日の件数が 2 に達したら残りは見送る。失敗(先に取られた等)したら次の候補へ進む |
| 5 | 自動予約の対象枠は空き通知しない | 対象期間(利用日 ≥ 今日+4 日)の枠は、**(a) 2 件あるので見送った、(b) 上位を取ったので見送った、(c) 試みたが失敗した、のいずれも通知しない**(失敗は結果カードで分かる)。**例外は (d) Pi の自動予約が動いていないとき**(回線断・停止)で、そのときだけ Actions が従来の通知カード(予約ボタン付き)を送る |
| 6 | 成功したら LINE に通知 | 既存の結果カード(`booking/src/result-flex.js`)を流用し、「自動予約」と分かる表記を加える。失敗時も同カード(既存どおり)。**利用日 = 今日+4 日 の成功カードには「⚠ 無料キャンセルは今日 23:59 まで」の警告と「キャンセル」ボタン**(フェーズ1.6 の署名付き postback `c|…` を流用)を載せる。**このボタンから取り消した枠も #9 の除外枠になる**(取り消したその枠を数分後に自動予約し直したら意味がない) |
| 7 | 平日は B、休日は A で予約 | **利用日**の曜日で決める(実行日ではない)。祝日は休日扱い(`lib/filter.js` の `isWeekendOrHoliday` を使う) |
| 8 | 除外日(追加要件) | LINE グループで **「じどう」** と送ると、現在の除外日一覧と「日を追加」ボタン(LINE の日付ピッカー `datetimepicker`, mode=date)が返る。各日に「解除」ボタン。除外日は **A/B 共通の 1 つのリスト**、**1 日単位**。除外日の枠は自動予約せず、従来の通知に回す。過ぎた日は自動で消す |
| 9 | LINE からキャンセルした枠は自動予約しない(追加要件) | フェーズ1.6 のキャンセル(「よやく」の一覧カードのボタン、**および #6 の成功カードのキャンセルボタン**。どちらも同じ Worker の取消処理を通る)が成功したら、その枠(公園・利用日・開始時刻)を **除外枠**として記録する。人が意図して手放した枠なので、空きとして再出現しても自動予約しない。**通知もしない**(本人が今消した枠の空き通知は雑音)。A/B 共通。枠の開始時刻を過ぎたら自動で消す。「じどう」の一覧に除外枠も表示し、「解除」で戻せる(取り直したいとき) |
| 11 | 日付境界と締切(2026-09-14 追加) | (a) 対象かどうかの判定は**「予約」を押す直前にもう一度**行う(見つけた時の判定を使い回さない)。23:59 に出た +4 日の枠を 00:01 に予約すると +3 日 = ペナルティ期間の予約になるため。日付が変わって対象外になった枠は予約せず、**Pi 自身が従来の空き通知カード(予約ボタン付き)を送る**(Actions は 23:59 の時点で「対象枠だから通知しない」と処理済みのことがある)。(b) **利用日 = 今日+4 日 の枠は 23:35 以降は自動予約しない**(取れても取消の猶予が無いため)。締切時刻は設定値(`lib/config.js`)にし、初期値 23:35(実測で 23:26〜23:32 に取消が少し固まっており、判定は予約直前なので 23:30 だとそこが拾えない。23:35〜23:50 の出現は 2 週間で 0 件)。締切後の枠は従来の通知に回す。+5 日以降の枠に締切は無い |
| 10 | 全体の上限 | **不要**(利用日ごと 2 枠だけ)。費用は本人が承知。不要な予約は「よやく」のキャンセルで人が消す |

その他の確定事項:
- 人数は既存と同じ **2 人**で申し込む
- reCAPTCHA v2 が出た回は既存の「🔐 確認が必要です」カードで人が対応(自動突破・回避は絶対にしない。既存方針のまま)
- 同じ枠を二重に試さない(再実行・重複起動に耐える。枠キー `facility|date|time` で冪等に)
- 予約サイトへの**ログインを伴う**自動アクセスは必要最小限(短時間に繰り返すと reCAPTCHA の点数が下がる)。空きの照会(ログイン不要の JSON)はこれに当たらない

## 3. なぜ Pi 側で 1 分おきか(実測データ、2026-08-31〜09-13 の state.json 履歴 5,214 回分)

- 監視対象の空きは 2 週間で 69 件出現し、63 件は他人に取られて消えた。61 件が「残 1 面」= 誰かのキャンセル分の争奪
- 見つけてから消えるまでの中央値 6 分。自動予約の対象(利用日 4 日以上先)は **8 割が 6 分以内に消える**。2 回のチェックの間に出て消えた枠は記録にすら残らない
- 出現は **23 時台に集中**(17/63)し、中身はほぼ「ちょうど 4 日後」の枠。無料取消の期限(利用日 4 日前の 23:59)直前にまとめて取り消されるため
- 今の経路(3 分待ち → Actions 90 秒 → Worker → Pi 40〜90 秒)は空きから予約完了まで 4〜6 分かかり、大半の争奪に負ける
- **Pi(常時稼働・自宅回線)で 1 分おきに照会し、見つけたら同じプロセスで即予約**すれば 1.5〜2.5 分に縮む。照会はログイン不要の軽い JSON(3 公園で 20 リクエスト程度/回)なので 1 分おきは常識の範囲。**30 秒より短くしない**
- Actions を 1 分おきにするのは不可(1 回 90 秒で実行が重なり、state.json のコミットも衝突する)。Actions の 3 分は通知用と、Pi が止まったときの受け皿として残す

## 4. 期待する動きの例

- 火曜 10:00 に「猿江 9/25(金) 19:00」が空いた → 利用日は 11 日先で対象 → Pi が B で自動予約 → 成功カード「🎾 予約完了(自動予約)」。Actions は通知カードを送らない
- 「猿江 9/16(水) 19:00」が空いた(今日 9/14 → 2 日先) → ペナルティ期間 → Actions が従来の通知カード(A/B ボタン付き)
- 9/14(日) 23:20 に「猿江 9/18(木) 19:00」が空いた → 利用日は今日+4 日で対象 → 平日なので B で自動予約 → 成功カードに「⚠ 無料キャンセルは今日 23:59 まで」とキャンセルボタン(猶予は 40 分)
- 土曜 9/27 に大島小松川 9 時・13 時・15 時と猿江 13 時が同時に空き、A はその日まだ 0 件 → 順は 大島 9 → 大島 13 → 大島 15 → 猿江 13 → 大島 9 時と 13 時を予約(2 件)。残りは通知しない
- 同じ例で大島 9 時が先に取られていた → 大島 13 時・15 時を予約
- 同じ例で A がその日に手動で 1 件持っていた → 大島 9 時だけ予約
- 9/27 が除外日 → 4 枠すべて Actions の従来の通知カード
- 「よやく」で「9/27 13:00 大島小松川」をキャンセル → 数分後にその枠が空きとして出現 → 除外枠なので自動予約せず、通知もしない。「じどう」の一覧に「9/27 13:00 大島小松川(キャンセル済み)」と出て、解除できる
- 23:20 に自動予約された「猿江 9/18(木) 19:00」を、成功カードのキャンセルボタンで 23:30 に取り消した → 同じく除外枠になる。23:31 に空きとして再出現しても Pi は取り直さない
- 9/13(土) 23:59 に「猿江 9/17(水) 19:00」が空いた → Pi が 00:01 に予約直前で再判定 → 利用日は +3 日 → 予約せず、Pi が従来の通知カードを送る
- 9/14(日) 23:40 に「猿江 9/18(木) 19:00」が空いた → +4 日だが 23:35 を過ぎている → 自動予約せず、従来の通知カード(人が押せば予約できる)
- Pi が止まっている(生存の合図が途絶) → Actions が対象期間の枠も従来の通知カードで送る(要件 5 の (d))

## 5. 設計の指針(この範囲で自由に決めてよい)

### 全体の分担

```
[Pi: 自動予約(新設)]  1 分おき: 空き照会(lib/scrape.js 相当) → 監視条件 → 前回との差分 → 対象/除外の振り分け → 並べ替え → 予約(既存 reserve) → 結果カード
                     毎回: Worker から除外日・除外枠を取得、Worker へ「生きている」合図(最終チェック時刻)を送る
[Actions: 通知(既存)] 3 分おき: 空き照会 → 差分 → Worker に「Pi の自動予約は生きているか」を聞く
                     生きていれば: 対象期間・除外日以外の枠だけ通知(ペナルティ期間の枠)。除外枠は通知しない
                     死んでいれば: 従来どおり全部通知(予約ボタン付き)
[Worker(既存に追加)] KV に 除外日・除外枠・Pi の最終チェック時刻 を持つ。「じどう」コマンド。キャンセル成功時に除外枠を追加
```

- **Pi の照会コード**: `lib/scrape.js` / `filter.js` / `config.js` / `date.js` は CommonJS で Node 標準機能だけ(依存は japanese-holidays)。Docker イメージには `booking/` しか入らないので、Dockerfile のビルドコンテキストに `lib/` を含めるか、共通コードの置き場を整理する。同じロジックを写して二重管理にしない
- **Pi の差分状態**: `state.json` とは別に Pi のボリューム(`/var/lib/booking`)に持つ。初回起動時は「いま見えている空き」を既知として扱い、まとめて予約しに行かない(起動直後の暴走防止)
- **予約の直列化**: ブラウザは 1 つ。自動予約の候補は行列に入れて 1 件ずつ。手動ボタン(`/book`)の予約と競合したら**手動を優先**し、自動は後ろに回す。1 件 40〜90 秒なので、照会の周期(1 分)と予約が重なる前提で組む(照会は止めない、予約は行列で)
- **2 件判定は実行直前に**: ログイン後に予約一覧(`rsvWGetCancelRsvDataAction.do` → `parseReservations`)を見て、その利用日のその人の件数を数える。既存の `verifyByList` と `reservation-list.js` を流用。高速経路(`site-inpage.js`)の中で一覧を取るのが自然。同一時間帯に既に予約があればサイトが断る(duplicate)が、数え上げで先に弾く
- **Pi 不達の判定(Actions 側)**: Pi の照会ループが毎回 Worker に最終チェック時刻を送り(署名付き。`/booking/register` の `x-booking-auth` と同じ流儀)、Actions は Worker から「最終チェックが N 分以内か」を取得する(N は 3〜5 分)。取れなければ死んでいる扱い(安全側 = 通知する)
- **除外日・除外枠の保存**: Worker の KV `BOOKING_KV`(新キー、例 `auto_exclusions`。日付の配列と枠キーの配列)。Pi と Actions は署名付き GET で取得。「じどう」の postback は `cancel-token.js` と同様の短い署名付き data(300 文字以内)。除外枠の追加はキャンセル成功の直後(`worker/src/index.js` の取消完了処理)に Worker が自分で行う。成功カードのキャンセルボタンも同じ取消処理に流すので、入口が 2 つでも記録は 1 か所で済む。**Pi の 1 分周期より先に KV に載る**ことを確かめる(取消 POST の完了 → KV 書き込み → LINE 返信の順)
- **キャンセル以外の手放し(サイトで直接取り消した等)への補強(推奨)**: Pi は自分が自動予約した枠を覚えておき、次に予約一覧を見たときにそれが消えていたら除外枠に加える(Worker へ登録)。これで LINE 以外から取り消した枠も取り直さない
- **結果カードのキャンセルボタン**: 成功カードの枠が利用日=今日+4 日のとき、フェーズ1.6 の `c|…` トークン(予約番号・利用日・時刻・公園・penaltyDay=3・期限)を作って載せる。予約番号は完了画面か一覧から取れる。Pi にはトークン生成の同等コード(Web Crypto ではなく node:crypto)が要るので、`cancel-token.js` の形式に合わせて実装しテストで一致を確かめる
- **設定の置き場**: 公園の優先順・時間帯の優先順・ペナルティ日数・1 日の上限・照会間隔は `lib/config.js`(または隣の定数ファイル)に 1 か所で。`PARKS` に優先順の項目を足すのが自然
- **ログ**: 利用者番号・パスワード・Cookie・トークンは出さない(既存方針)。自動予約の判断理由(なぜ見送ったか)はログに残す
- 通知カード側(`lib/notify.js`)は変更を最小に。振り分けは `check.js` で行い、`sendLineMessage` には通知する枠だけ渡す
- Pi の生存監視(`worker/src/monitor.js`)は既存のまま。自動予約の照会ループの停止も同じ ⚠️ で知らせるか、別の合図にするかは決めて文書化する

## 6. 実装・確認の進め方

1. 設計を短くまとめて本人に確認(特に: 行列と手動優先、Pi 不達の判定、除外の UX、Docker への `lib/` の入れ方)
2. ユニットテスト(`node --test`): 振り分け(ペナルティ境界 = 今日+3 は対象外、+4 は対象)、並べ替え(公園→時間帯)、2 件上限(既存件数を考慮)、平日/休日→予約者、除外日・除外枠、日付境界(23:59 検出 → 00:01 実行で見送り + 通知)、+4 日の 23:35 締切、初回起動の暴走防止、行列と手動優先、署名付きデータ、キャンセルトークンの Worker/Pi 間の一致、Actions の「Pi 生存」判定と通知の振り分け。既存テストは `booking/test/`, `worker/test/`、ルートは `npm run test:logic`(モック dry-run)
3. Pi 側に dry-run(照会と振り分けだけ表示、予約しない)の起動方法を用意する。`MOCK_SLOTS_FILE` 相当も
4. 実機テストは**利用日が 4 日以上先の枠**で行う(自動予約の対象は常にこの範囲なので、テスト予約は当日中なら無料で取り消せる。取消は LINE の「よやく」→「キャンセル」)。**テスト予約も本物の予約**なので、事前に本人へ枠と回数を伝えて了解を取る。**利用日=今日+4 日 の枠は避ける**(取消猶予が短い)
