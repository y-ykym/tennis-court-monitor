# フェーズ2「予約支援(半自動予約)」引き継ぎドキュメント

新しいセッションでフェーズ2の設計・実装を始めるための引き継ぎ。方針は検討・合意済みで、
このドキュメントの「決定事項」に従って進めてよい。前提知識は「現状のシステム」と
「既存資産」を読めば揃う。

## 1. フェーズ2でやること(合意済みの方針)

**「新しい空きのLINE通知 → ボタンをタップ → 人間はreCAPTCHAと確定だけ」の半自動予約。**

- LINEのFlex通知カードの各枠に「予約する」ボタン(URI)を付ける
- タップすると予約支援サーバーが起動し、Playwright制御のheadful Chromeが
  **ログイン〜対象枠の選択〜予約確認画面の直前まで自動遷移**する
- その画面を **noVNC** でスマホのブラウザにそのまま配信する
- **人間がやるのは reCAPTCHA のチェックと「確定」ボタンのタップだけ**
- 完全自動予約はしない(下記「越えてはいけない一線」参照)

### 越えてはいけない一線(この順で強い制約)

1. **reCAPTCHAの機械突破・回避は絶対にしない**。人間が自分の予約のために自分で解く設計のみ
2. **最終確定ボタンは必ず人間が押す**(自動で押さない)
3. 「事前に枠を選択して待機」はしない(セッション切れ・仮押さえ問題)。**タップ起点のオンデマンド遷移**のみ
4. 着手前に**都の予約システムの利用規約**で自動操作の扱いを確認する(未確認。要ユーザー確認)

## 2. アーキテクチャ(決定)

```
[監視系(稼働中・変更しない)]
cron-job.org --(3分おき workflow_dispatch)--> GitHub Actions(check.js)
  --(空き照会 JSON API)--> 都営予約サイト
  --(新規空きのみ Flex通知)--> LINEグループ(A・B・ボット)
  --(同時に /warmup を叩く)--> 予約支援サーバー ← フェーズ2で追加する連携

[予約支援系(新設)]
LINE Flexカード「予約する」ボタン(署名付きURL、枠情報入り)
  --> Cloud Run(Webアプリ + Playwright headful Chrome + Xvfb + noVNC)
  --> ログイン〜対象枠選択まで自動遷移 --> noVNCでスマホに画面配信
  --> 人間が reCAPTCHA + 確定
```

### ホスティング: **GCP Cloud Run**(決定)

- ゼロスケール(使わない間は0円)+ WebSocket対応 + HTTPS標準装備がこの用途に最適
- **max instances = 1** + セッションアフィニティ(`/book` とnoVNCのWebSocketが同一インスタンスに届く必要がある)
- 認証情報(都サイトの利用者番号・パスワード)は **GCP Secret Manager**
- リージョンは東京(asia-northeast1)

### コールドスタート対策: **通知時ウォームアップ**(決定)

- Cloud Runのコールドスタート(20〜60秒)+自動遷移(30〜60秒)は、素朴に作ると
  人間の手動予約(2〜3分)と互角になってしまう
- 対策: **GitHub Actionsが通知を送る瞬間に、Cloud Runの `/warmup` も叩く**
  (check.js または workflow に1ステップ追加)。人間がタップする頃には起動済みになり、
  体感の待ちは自動遷移の残り(〜30秒)だけになる
- ウォームアップは「監視対象の空きが出たとき」しか走らないので、0円運用は崩れない

### セキュリティ(決定)

- Flexボタンの URL には**署名付きトークン**(枠情報+有効期限をHMAC署名)を入れ、
  第三者がURLを踏んでも起動しないようにする
- noVNC にはパスワードを設定する
- 都サイトの認証情報はSecret Managerのみ。リポジトリ・LINEメッセージには絶対に入れない

## 3. ユーザーの利用フロー(合意済みのUX)

1. LINE通知が届く(この時点で裏でウォームアップ開始)
2. Flexカードの行きたい枠の「予約する」ボタンをタップ
3. ブラウザで待機画面(数秒〜30秒。裏でログイン〜枠選択まで自動遷移)
4. noVNCで予約サイトの確認画面がスマホに表示される
5. 人間: reCAPTCHAチェック → 「確定」タップ
6. 完了。予約完了メールは都のシステムから通常どおり届く

失敗系: 先に取られていたら画面がそのまま「予約あり」表示になる(誤予約は構造上起きない)。
タップが遅れてセッションが切れていたら、待ちが1〜2分に伸びるだけで流れは同じ。

## 4. 着手前に確認・計測すべきこと(未解決の宿題)

1. **利用規約**: 自動操作(遷移の自動化)の扱い。違反ならアカウント停止リスクがあるため最重要
2. **reCAPTCHAの出現箇所**: ログイン時か予約確定時か(自動遷移の「止めどころ」が変わる)。
   ユーザーは予約フローにreCAPTCHAがあると認識している
3. **セッション寿命の実測**(15〜30分と推定)と、枠選択が仮押さえ扱いになるか
   (ペナルティ制度があるため、選択放置の影響を確認)
4. AとBが同時にタップした場合の挙動をどうするか(同一インスタンス・同一画面を共有する)

## 6. 現状のシステム(フェーズ1/1.5、稼働中)

- **監視(フェーズ1)**: cron-job.orgから3分おきに`workflow_dispatch`でGitHub Actionsを起動
  (**GitHubのschedule(cron)はこのアカウントで極端に間引かれるため使っていない**。
  5分指定で実効3〜4時間。検証用リポジトリ `y-ykym/cron-canary` が観測装置として存続中で、
  正常化を確認したらscheduleに戻す手順がREADME運用メモにある)
- 取得はPlaywright不使用。サイト内部のJSON APIを素のHTTP(Node標準fetch)で叩く
- 通知はグループLINE宛て(`LINE_USER_ID` SecretにグループID `C〜`)のFlex Message
- state.jsonはActionsボットが自動コミット(ローカル作業前に `git pull` 必須)
- **フェーズ1.5**: `worker/` にCloudflare WorkersのLINEボット(「よやく」で予約一覧をFlexで返信)。
  Secretsは `wrangler secret put` で登録済み(トークン・利用者番号・パスワード)
- コストは全体で0円。LINE無料枠は月200通。cron-job.orgのPATは期限1年(失効時はcron-job.orgから失敗メール)

## 7. 実装の進め方(推奨順序)

1. 宿題1〜3(規約・reCAPTCHA箇所・セッション寿命)の確認。特に規約NGなら中止判断
2. ローカルで予約フローの自動遷移をPlaywrightで組む(**確定は絶対に押さない**。
   確認画面到達までをテストし、直前で止める)。`worker/src/site.js` のログイン処理を移植
3. コンテナ化(Chrome+Xvfb+noVNC+Webアプリ)してCloud Runへ。署名付きURL・Secret Manager・
   max instances=1・セッションアフィニティを設定
4. `lib/notify.js` に予約ボタン追加、`check.js`(またはworkflow)にウォームアップ呼び出し追加
5. モック枠でエンドツーエンド確認(通知→タップ→noVNC→CAPTCHA画面表示まで)

## 8. 予約サイトの基本情報(再掲)

- 入口: https://kouen.sports.metro.tokyo.lg.jp/web/index.jsp (2023年リニューアル版。URLは旧来のまま)

### 2026-09-03(夜) 方式決定: 半自動 noVNC(ユーザー判断・確定)

- 前提(確定): DC IP では「予約」送信後に v2 チェックボックスが必ず出る(実予約 0/3)。人間らしい操作でも覆らない
- 構成: **Cloud Run の1コンテナ**(Node Webアプリ + Xvfb + headful Chromium + x11vnc + noVNC)。

- `reserve.js` に `onConfirm` フック(予約確認画面で人間に制御を渡し、完了画面への遷移を待つ)を追加して流用
- 実装ファイル: `booking/src/token.js`(HMAC署名URL)、`booking/server/server.mjs`、`booking/Dockerfile`、`booking/docker-entrypoint.sh`
- 手順: ローカル Docker でビルド・動作確認 → GCP(gcloud導入・プロジェクト・Secret Manager・Cloud Run デプロイ。ユーザー手作業、クレカ登録が要る)
