## 2. 予約ボタンを押したときの流れ

```
LINE 通知カード「ゆうたそで予約」(postback。ブラウザは開かない)
 → Worker: 署名を確かめ、Pi の /book を叩く → LINE に「🎾 受け付けました」と返信
   (Pi に届かなければ「予約サーバーに繋がりませんでした。1〜2分後にもう一度」)
 → Pi(booking コンテナ): ログイン → 枠選択 → 予約内容確認 → 「予約」(約 40〜90 秒)
   ・reCAPTCHA v2(画像問題)が出たときだけ LINE に「🔐 確認が必要です」カード → ボタンで noVNC 画面を開いて人がチェック(8 分以内)
   ・完了画面に到達しなくても、予約の確認一覧を開いて入っていれば成功と判定する(2026-09-13 21:32 の教訓)
 → LINE に結果カード(🎾 予約完了 / ⚠️ 予約できませんでした)。回線断で送れなければ 1 分ごとに再送(最長 6 時間)
```

**2026-09-25 の事故と対策**: 12:11 に亀戸 9/30(水) 13:00 が「手動予約」として成立(誰も操作していない)。Cloudflare の Worker ログ(Observability → Events)で、
LINE のリンク先読みロボット(User-Agent `facebookexternalhit/1.1;line-poker/1.0`、LINE Corporation の回線)が 9/13 のテストで作った署名 URL `GET /book?token=…&person=A` を開いたと確定。
当時の Worker は「URL を開いただけで予約開始」だった。同日 Worker の `GET /book` を廃止(410 の案内だけ返し、Pi へ中継しない)し、通知側の URL 型ボタンの予備経路も撤去。
予約を始める入口は **LINE の postback `book|<token>`(ログでは `POST /webhook`)だけ**になった。自動予約(Pi)には無関係。
「誰も操作していないのに予約された」ときは Worker ログの該当時刻の Method/Path/User-Agent を見る(ダッシュボードは Claude の内蔵ブラウザからは会社ポリシーで開けないので本人が画面を貼る)。

Pi 側の経路: Worker → Cloudflare Tunnel(quick tunnel、URL は起動ごとに変わる)→ Pi。Pi の `registrar` が 4 分ごとに現在の URL を Worker の KV に登録(TTL 10 分)。
`tunnel-watchdog.timer`(1 分ごと)がトンネルの自力復帰不能を検知して再起動する。

### KV の書き込み枠(1 日 1,000 回)について

2026-09-16 に上限超過で 10 時間止めた(詳細は§5)。**リセットは UTC 0:00 = 日本時間 9:00** なので、夜に当たると翌朝 9 時まで復旧しない。

- 今の使用量: URL 登録 360 回/日(4 分ごと)+ 監視 24 回/日 + 除外の操作ぶん = **400 回弱**
- 「1 分ごとに KV へ書く」類の機能を足すと 1,440 回で即アウト。足すなら先にこの表を計算し直すこと
- `registrar` が二重に起動しても倍になる。`docker compose ps` で 1 つであることを確認
- 上限に当たっても監視が壊れないよう、`worker/src/monitor.js` は「保存 → 送信」の順で、送れなかったぶんは次回に再送する

## 5. 既知の癖・注意

- **自宅回線(SoftBank Air)は夜に不安定**(2026-09-13 は 21〜23 時に数分の断が複数回)。**2026-09-26 に回線が安定する予定**。それまで「繋がりません」が出たら 1〜2 分後に押し直す
- **Pi の Chromium は自動操作の目印(`navigator.webdriver`)を消してある**(compose の `IGNORE_DEFAULT_ARGS` / `CHROME_ARGS`)。これが無いと reCAPTCHA v2 が頻発する
- 高速経路(`FAST_PATH=1`、ページ内 fetch)で運用。v2 が頻発したら `'0'` に落として様子を見る(README §8)
- 「予約」後に確認画面のままでも成立していることがある → 必ず一覧で確認してから成否を決める(実装済み)
- テスト予約はテニスなら利用日の 4 日前までならペナルティなしで取り消せる(取消に費用はかからない。遅れるとペナルティ 1 点)。取消は LINE の「よやく」→「キャンセル」
- 実サイトへの自動アクセス(dry-run・探針)を短時間に繰り返すと reCAPTCHA の点数が下がる。必要最小限に
- `wrangler tail` は自宅回線の瞬断で落ちやすい。Worker の挙動を確かめるなら KV に書き残す方式か、テストで
- **KV の書き込みは 1 日 1,000 回まで(無料枠)**。2026-09-15 に Pi の生存を 1 分ごとに KV に書いていて 22 時ごろ超過し、Worker が 500 を返して Pi が除外一覧を取れず「予約しない」判定になった(dry-run 中に発見)。
  以後、Pi の生存は KV に書かず Worker が Pi の `/auto/status` を直接聞く。新しく KV に定期的に書く仕組みを足すときは、この上限を必ず数える
- **2026-09-16 の顛末(監視まで巻き込んだ)**: 上の超過で URL 登録(KV 書き込み)も通らなくなり、22:55 ごろ `booking_url` が TTL 切れ → 23:00 の監視が ⚠️。
  リセットは UTC 0:00 = **日本時間 9:00** なので、9:00:03 の登録成功まで約 10 時間ダウン。さらに当時の `monitor.js` は「送信 → 保存」の順だったため、
  ①保存できず ⚠️ を毎時くり返して LINE の通数上限(200 通)を使い切り、②その上限で復帰通知が送れず毎時やり直し、15:00 にやっと届いて **「停止 約960分」(実際は約10時間)**と水増し表示された。
  対策として (a) URL 登録を 2 分 → **4 分**ごと(TTL 5 → 10 分、720 → 360 回/日)、(b) `monitor.js` を **保存 → 送信**の順にし、送れなかった知らせは `pending` に積んで次の回に再送、停止時間は復帰を検知した時点で確定、を入れた(テスト済み)
- **コンテナが `Restarting` を繰り返して自力で戻らないとき**: 前回の終了時に Xvfb が `/tmp/.X99-lock` を残すと、
  次の起動が「Server is already active for display 99」で必ず失敗する。コンテナの中身は再起動しても残るので、作り直すまで永久に直らない。
  2026-09-19 のケース組み込み(電源断)で発生し、17 回ループして LINE に ⚠️ が出た。
  entrypoint に消す処理を入れて解決済み(`booking/docker-entrypoint.sh`)。再発したら `docker compose up -d --force-recreate booking`。
  ログに何も出ないまま `exit 1` するのが特徴で、原因は `docker cp pc-booking-1:/tmp/xvfb.log - | tar -xO` で見える
- サイトへのアクセス量は Actions(3 分おき・18 リクエスト)+ Pi(7〜翌 1 時は 1 分、1〜7 時は 3 分おき・18 リクエスト)で合計 平均 0.35 回/秒(2026-09-24 時点。7〜21 時を 2 分 → 1 分にした。ピークは変わらない)。
  予約サイトの利用規約は 2026-09-15 に本人が確認し、自動アクセスの禁止条項は無かった。取得失敗が続くようになったら相手側の制限を疑い、間隔を広げる(`lib/config.js`)
