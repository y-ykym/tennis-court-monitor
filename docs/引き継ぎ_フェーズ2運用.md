## 2. 予約ボタンを押したときの流れ

```
LINE 通知カード「ゆうたそで予約」(postback。ブラウザは開かない)
 → Worker: 署名を確かめ、Pi の /book を叩く → LINE に「🎾 受け付けました」と返信
   (Pi に届かなければ「予約サーバーに繋がりませんでした。1〜2分後にもう一度」)
 → Pi(booking コンテナ): ログイン → 枠選択 → 予約内容確認 → 「予約」(約 40〜90 秒)
   ・reCAPTCHA v2(画像問題)が出たときだけ LINE に「🔐 確認が必要です」カード → ボタンで noVNC 画面を開いて人がチェック(8 分以内)
   ・完了画面に到達しなくても、予約の確認一覧を開いて入っていれば成功と判定する(2026-09-13 21:32 の教訓)
 → LINE に結果カード(🎾 予約完了 / ⚠️ 予約できませんでした)。回線断で送れなければ 1 分ごとに再送(最長 6 時間)
```

Pi 側の経路: Worker → Cloudflare Tunnel(quick tunnel、URL は起動ごとに変わる)→ Pi。Pi の `registrar` が 2 分ごとに現在の URL を Worker の KV に登録(TTL 5 分)。
`tunnel-watchdog.timer`(1 分ごと)がトンネルの自力復帰不能を検知して再起動する。

## 3. 設定値の所在(値はどこにも平文で書かない)

| 値 | ある場所 | 備考 |
|---|---|---|
| `BOOKING_SIGNING_SECRET`(署名鍵) | GitHub Secrets / Worker Secrets / Pi の `.env` の 3 か所に同じ値(2026-09-13 に作り直し、指紋 107cf15a) | 読み戻せるのは Pi の `.env` だけ |
| `LABEL_A` / `LABEL_B`(呼び名) | GitHub Secrets / Worker Secrets / Pi の `.env` | ボタンの文字になる |
| `SITE_USER_*` / `SITE_PASS_*` | Worker Secrets / Pi の `.env` | **パスワードは本人が入力**。Claude は値を見ない・打たない |
| `LINE_CHANNEL_ACCESS_TOKEN` / `LINE_USER_ID`(=グループ ID C〜) | GitHub Secrets / Worker(`LINE_GROUP_ID`)/ Pi の `.env` | Pi から結果カードを push するのに使う |
| `BOOKING_BASE_URL` | GitHub Secrets | `https://tennis-reservation-bot.y-ykym.workers.dev` |
| Worker の KV `BOOKING_KV` | `booking_url`(Pi の現在の URL)、`monitor_state`(監視の状態)、`auto_exclusions`(除外日・除外枠)、`auto_alive`(Pi の最終チェック)、`auto_mode` | `wrangler kv key get --remote --namespace-id 97e0d8dae665476797bae9dc168c560b <key>` |
| Pi の `.env` の `AUTO_BOOKING` | `off` / `dry-run` / `on`(フェーズ3 のモード) | 変えたら `docker compose up -d`(再ビルド不要。env_file の読み直しのため `up -d` で再作成される) |

**`.env` の控えはユーザーがパスワード管理アプリ等に持つ**(未実施なら促す。Pi の SSD が壊れると全部作り直しになる)。

## 4. 日常の確認とコマンド

Mac から(会社 Mac は SD カード禁止だが SSH は可):

```bash
ssh yu@homepi.local                                # Pi に入る(鍵認証。パスワード認証は閉じてある)
cd ~/tennis-court-monitor/booking/pc && ./pi-check.sh   # 起動ディスク・温度・OS 更新・Docker・Tunnel・Worker 登録を一覧
docker compose logs -f booking                     # 予約フローのログ(利用者番号・パスワードは出ない)
curl -s https://tennis-reservation-bot.y-ykym.workers.dev/booking/status   # Worker から見た Pi の登録(registered:true なら届く)
```

コードを変えて Pi に反映するとき(**毎時 0 分前後は避ける**。監視と重なって ⚠️ が誤って届く):

```bash
# Mac: commit → push(state.json の自動コミットで origin が進むので、必ず rebase)
git pull --rebase origin main && git push
# Pi(scp で直接ファイルを置かない。git pull が失敗して古いコードでビルドしてしまう)
ssh yu@homepi.local 'cd ~/tennis-court-monitor && git pull --ff-only && cd booking/pc && docker compose build booking && docker compose up -d'
```

Worker: `cd worker && npm test && npx wrangler deploy`。通知側(lib/)は push すれば次の Actions 実行から反映。

フェーズ3 の確認(Pi 上で):

```bash
docker compose logs -f booking | grep '\[auto\]'      # 1 分おきの照会と振り分け(見送りの理由も出る)
curl -s http://localhost:8080/auto/status | jq         # mode・最終照会・除外一覧の件数・行列
```

Docker のビルドコンテキストはリポジトリ直下に変わった(`lib/` を同梱するため)。`docker compose build booking` のコマンドは変わらない。

## 5. 既知の癖・注意

- **自宅回線(SoftBank Air)は夜に不安定**(2026-09-13 は 21〜23 時に数分の断が複数回)。**2026-09-26 に回線が安定する予定**。それまで「繋がりません」が出たら 1〜2 分後に押し直す
- **Pi の Chromium は自動操作の目印(`navigator.webdriver`)を消してある**(compose の `IGNORE_DEFAULT_ARGS` / `CHROME_ARGS`)。これが無いと reCAPTCHA v2 が頻発する
- 高速経路(`FAST_PATH=1`、ページ内 fetch)で運用。v2 が頻発したら `'0'` に落として様子を見る(README §8)
- 「予約」後に確認画面のままでも成立していることがある → 必ず一覧で確認してから成否を決める(実装済み)
- テスト予約はテニスなら利用日の 4 日前まで無料で取り消せる。取消は LINE の「よやく」→「キャンセル」
- 実サイトへの自動アクセス(dry-run・探針)を短時間に繰り返すと reCAPTCHA の点数が下がる。必要最小限に
- `wrangler tail` は自宅回線の瞬断で落ちやすい。Worker の挙動を確かめるなら KV に書き残す方式か、テストで
